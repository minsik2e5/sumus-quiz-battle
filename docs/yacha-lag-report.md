# 야차 대회 렉 원인 보고서 (v13.212.0, 2026-11-03)

## 한 줄 원인
메인 상태 객체(하나뿐, 한 줄로 처리)가 **POST 하나마다 상태를 깊게 복사**했다. 운영 상태 13.5MB 중 지난 연습 기록만 빼고
숙련도 2.35MB까지 복사해서 POST 하나에 CPU 약 85ms. 놀이터 **'보기'(인형뽑기 · 사냥 첫 화면, 낚시 안내, 10초 맞추기 ping)까지
POST**라서 누를 때마다 복사하고 저장을 기다렸다. 대회를 기다리는 학생들이 놀이터를 같이 하면 줄이 밀려 대회 판 시작 · 결과 · 놀이터가
모두 1초 넘게 걸렸다("전반적으로 다 렉").

## 증상(선생님)
- 대회 중 모든 학생, 와이파이 · 데이터 모두. "단어를 눌렀는데 렉", "지금 전반적으로 게임 다 렉".
- 운영 `/api/health`(대회 중): 상태 13,477KB(sessions 9.9MB · mastery 2.35MB · profiles 0.59MB), 쓰기 1.2%(`ok`),
  Supabase 백업 실패 6번(`voca_v13_state_revision: TimeoutError (0 KB)`, 12초 제한의 작은 요청).

## 고친 것(우선순위 = 효과 순)
1. **숙련도 복사 빼기**: 숙련도(mastery)를 학생 묶음마다 얼려 같이 쓰고, 요청한 학생(로그인 세션) 묶음만 복사. 다른 학생 숙련도를
   고치는 변경(선생님 재채점 등)은 얼린 묶음을 고치려다 오류가 나고, 예전 복사로 처음부터 다시 해서 결과가 같다.
   저장할 때도 얼린 묶음은 지난번 글을 다시 쓴다.
2. **놀이터 '보기'를 가볍게**: 10초 맞추기 ping은 읽기 경로(복사 · 저장 없음). 인형뽑기 · 사냥 첫 화면, 낚시 · 사냥 안내는 그 학생
   프로필 사본에서 해 보고 그대로면 저장 없이 답, 바뀌었으면(새 사냥 지도, 처음 본 안내) 예전처럼 저장.
   시작 · 집게 · 던지기 · 판 받기 · 끝내기는 그대로 저장 경로.
3. **Supabase 백업이 요청과 겹치지 않게**: 학생 요청을 처리하는 중(또는 1초 안)이면 2초씩, 최대 20초 미룬다(대회처럼 요청이 끊이지
   않아도 20초 뒤에는 한다). 실패 뒤 다시 하기는 그대로(2초부터 두 배, 최대 1분).

규칙 · 보상 · 판정 코드(service · 엔진)는 바꾸지 않았다. 기존 검사 전부 통과.

## Supabase 백업 실패(별도 문제)
- 실패한 것은 `voca_v13_state_revision`(백업 번호 확인, 0KB, 12초 제한). 메인 객체가 바빠서라기보다 **Supabase가 12초 안에 답하지
  않는 것**으로 보인다(업로드 전 단계라 CPU는 거의 안 씀). 학생 데이터는 Cloudflare 로컬 저장이 기준이라 지금 잃는 것은 없다.
- 다시 성공하는 조건: Supabase가 이 번호 확인에 12초 안에 답하면 다음 시도(최대 1분 간격)에서 방식이 'parts'로 정해지고, 그 사이
  바뀐 조각만 올린 뒤 `supabase_failures 0`, `supabase_lag_sec 0`, `supabase_last_ok_at`이 채워진다.
- 선생님 확인: Supabase 대시보드에서 프로젝트가 일시정지(Paused)나 점검 중이 아닌지.
