# 렉 방지 규칙 (v13.212.0부터)

## 왜 필요한가
학생 데이터는 Cloudflare의 **메인 상태 객체 하나**가 맡고, 요청을 **한 번에 하나씩** 처리한다(유료 플랜이어도 같다).
요청 하나가 오래 걸리면 그 뒤의 모든 학생이 기다린다. 2026-11-03 대회 때 렉이 이 때문이었다(`docs/yacha-lag-report.md`).
기능이 늘어도 다시 그러지 않도록 아래를 지킨다. ✅ 표시는 `npm run check` · `check:load`가 자동으로 막는 것이다.

## 기능을 만들 때 지킬 것
1. **보기는 GET으로.** 화면을 여는 요청(첫 화면 · 목록 · 순위 · ping)은 GET으로 만든다.
   - 꼭 POST여야 하면 `server/mutation-coordinator.mjs`에 등록한다.
     - 아무것도 바꾸지 않으면 `READ_POSTS`
     - 그 학생 프로필만 가끔 바꾸면 `VIEW_POSTS`
   - ✅ `…/home` · `…/ping` · `…/board` · `…/guide` 같은 이름의 POST가 등록돼 있지 않으면 검사가 실패한다(예외는 `server/perf-budget.mjs`에 이유를 적는다).
2. **쓰기 요청은 요청한 학생 것만 고친다.** 다른 학생의 숙련도 · 기록을 고치는 일(선생님 재채점 등)은 드문 선생님 작업에만 둔다.
   그런 요청은 상태를 크게 복사해서 다시 하므로 느리다.
3. **새 데이터 묶음에는 예산과 정리 방법을 정한다.**
   - 상태의 맨 위 묶음(예: `clawNews`, `timingDaily`)을 새로 만들면 `server/perf-budget.mjs`에 크기 예산(KB)과 정리 방법을 적는다. ✅ 적지 않으면 검사가 실패한다.
   - 학생 한 명의 데이터는 그 학생 프로필 안이나 학생별 묶음에 둔다.
   - 목록은 개수 상한(최근 N개)이나 기간(며칠 지나면 지움)을 둔다. **끝없이 쌓이는 목록은 만들지 않는다.**
4. **무거운 계산은 홈 화면 GET에서만, 캐시해서.** 전체 학생 · 전체 기록을 훑는 계산(순위, 학교 대항전, 칭호 전체 판정)은 쓰기 요청 안에서 하지 않는다.
   GET에서 할 때도 시간 기준 캐시(예: 1분)를 쓴다.
5. **자동 새로고침 간격.** ✅ 화면이 서버에 자동으로 묻는 간격은 3초 이상이다.
   - 학생 화면은 20초 이상, 전체 새로고침은 2분을 기준으로 한다.
   - 화면이 안 보이면(다른 탭 · 화면 꺼짐) 묻지 않는다.
6. **실시간은 방 객체로.** 대결 · 던전 · 교실 게임처럼 1초에 여러 번 오가는 일은 따로 된 방 객체에서 하고, 끝날 때 결과만 메인 객체에 한 번 보고한다.
7. **부하 검사 상한을 올리지 않는다.** ✅ `npm run check:load`의 대회 + 놀이터 시뮬레이션(`server/tournament-load.mjs`)이 경로별 p95 상한을 본다.
   상한을 올려야 하면 PR에 이유를 쓰고 선생님 확인을 받는다.
8. **연출은 퀄리티를 지킨다.** 화면이 무거우면 저사양 폰에서만 자동으로 낮춘다(기존 규칙).

## 운영에서 지켜볼 숫자 (`/api/health`)
| 항목 | 정상 | 넘으면 |
|---|---|---|
| `storage.upgrade` | `paid_upgrade` · `fix_data` 모두 false | `reasons`에 할 일이 한국어로 나온다(유료 업그레이드 또는 데이터 정리) |
| `storage.state_budget.ok` | true | 넘은 묶음(`over`) · 예산표에 없는 묶음(`unknown`)을 정리하거나 예산을 다시 정한다 |
| `storage.state_kb` | 25,000 아래 | 정리 규칙을 손본다(연습 기록 보관 기간 등) |
| `write_level` | `ok` | `warn`(70%)이 자주 뜨면 업그레이드를 검토한다(아래) |
| `storage.mastery_retries` | 재채점할 때만 조금씩 는다 | 계속 늘면 어떤 요청이 다른 학생 숙련도를 고치는지 찾는다 |
| `storage.supabase_failures` | 0 | Supabase 대시보드(일시정지 · 점검)를 확인한다 |
| `storage.supabase_status` | `ok` | `paused_suspected` · `failing`이면 `docs/supabase-backup-runbook.md` 순서대로(6시간 넘으면 선생님 화면에도 경고) |

## 계속 지키는 방법
- AI 작업 메모(`CLAUDE.md`)에 넣어 두어 매 세션 처음에 읽는다.
  - 새 기능 PR마다 "렉 방지 점검" 칸에 이 규칙을 지킨 방법을 적는다.
  - `check:load` 숫자를 적는다.
  - 운영 숫자가 나오면 업그레이드 · 정리가 필요한지 먼저 말한다.
- ✅ 표시 규칙은 검사가 막아서, 어기면 `npm run check`가 실패해 PR을 올릴 수 없다.
- 선생님 화면의 '오늘 서버 저장량이 많아요' 안내에 업그레이드 기준이 함께 나온다.

## 언제 업그레이드하나 (Cloudflare Workers 유료, 최소 월 5달러)
유료로 바꿔도 **객체 하나의 속도는 같다.** 렉이 아니라 **무료 한도 때문에 서비스가 멈추는 것**을 막는 용도다. 아래 중 하나면 업그레이드한다.
- 선생님 화면에 '오늘 서버 저장량이 많아요(70% 이상)'가 일주일에 한 번 넘게 뜬다.
- Cloudflare 대시보드에서 Durable Objects 요청이 하루 무료 한도(10만 건, 대결 답 메시지 포함)의 70%를 넘는 날이 생긴다.
- "Error 1101"이 한 번이라도 다시 난다(2026-10-12에 쓰기 한도를 넘어 일어났다).

## 몇 명까지 괜찮나 (2026-11-03 측정, v13.212.0)
대회 32명 + 기다리는 동안 놀이터 + 연습 + 놀이터만 하는 학생을 늘려 가며 한 번에 쟀다. 모든 학생이 2.5초마다 누르는 가장 바쁜 경우다.

| 동시에 활동하는 학생 | 상태 크기 | 대회 판 열기 p95 | 사냥 첫 화면 p95 | 판단 |
|---|---|---|---|---|
| 40명(v13.210, 고치기 전) | 12MB | 1,945ms | 1,664ms | 렉 |
| 40명 | 12MB | 238ms | 258ms | 여유 |
| 80명 | 14MB | 255ms | 240ms | 여유 |
| 120명 | 17MB | 280ms | 249ms | 괜찮음 |
| 180명 | 20MB | 656ms | 424ms | 느려지기 시작 |

- 이 컴퓨터의 Node 값이다. Cloudflare는 더 느릴 수 있어 넉넉하게 **동시 활동 약 80명까지 여유**, 100명을 넘으면 다시 잰다.
- 상시 동시 활동이 100명을 넘게 되면 업그레이드로는 안 풀린다. 데이터를 학생별 객체로 나누는 설계를 검토한다(큰 작업).
