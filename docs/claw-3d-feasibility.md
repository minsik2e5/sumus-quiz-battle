## 1. 저사양 기준

| 기기 | CPU · GPU · 메모리 | 이 문서에서의 근사 |
|---|---|---|
| 갤럭시 A13 · A14 · A15 급 | Exynos 850 · Helio G80/G99, Mali-G52/G57 MC2, 3~4GB | Chrome CPU 4× ~ 6× 느리게 |
| 아이폰 SE2 · 8 | A13 · A11 (CPU는 빠름, 메모리 2~3GB, 화면 750×1334) | 4×보다 빠름. 메모리가 적어 큰 텍스처가 위험 |
| 학교 크롬북 | Celeron N4020 · MT8183, Intel UHD 600 · Mali-G72, 4GB | 4× ~ 6× |

Chrome 스로틀링은 CPU만 느리게 한다(그래픽은 그대로). 측정 환경의 그래픽은 소프트웨어(헤드리스)라 그리기는 오히려 불리하다. 그래서 실제 폰은 그리기 쪽이 이 표보다 낫고, CPU(물리 · 자바스크립트)는 이 표와 비슷하다고 본다.

### 번들 · CSP · 미리 받기(sw.js)

- 이 앱은 CSP `script-src 'self'`라 바깥 CDN을 못 쓴다 → 라이브러리를 저장소에 같이 넣고 `'self'`로 부른다.
- `public/vendor/`에 두면 `server/build-assets.mjs`의 `onDemand` 규칙에 걸려 **미리 받기(precache)에 들어가지 않고** 인형뽑기에 처음 들어갈 때만 받는다. 앱 첫 실행 크기는 그대로.
- 2.5D 물리: 첫 입장 때 +25KB(학교 와이파이에서 0.1초 안팎). 진짜 3D: +160KB ~ 0.7MB 코드 + 모델 2~5MB → 처음 입장 수 초, 모델은 따로 나눠 받아야 한다.

## 4. 서버 판정과 "결정된 물리"

지금은 서버가 판 배치(판 id → `roundLayout`)와 잡힘 · 놓침을 정한다. 물리를 화면이 돌리면 ① 인형 자리가 서버 좌표와 어긋나 "보이는 인형 ≠ 서버가 잡은 인형"이 되고 ② 물리가 "잡혔어야 할" 인형을 떨어뜨릴 수 있다. 그래서 물리는 **결과를 정하지 않고 결과에 맞춰 움직인다**:

1. **같은 시작**: 판 id → 같은 종류 · 자리 · 기울기. 고정 시간 간격(1/60초), 씨앗 난수(Math.random 안 씀) → 같은 기기에서는 늘 같은 장면(재현 검사 OK). 기기마다 소수 끝자리가 다를 수 있으나 결과에는 영향이 없다(아래 2 · 3).
2. **앵커 스프링**: 인형마다 서버 자리(x · y · 층)에 약한 스프링을 단다. 흔들리고 밀려도 서버 반지름(R)의 0.3배 안으로 돌아온다 → 조준(`touchAt`)이 보이는 그림과 맞다. 뽑힌 자리 둘레는 서버 `settleNudges`만큼 앵커를 옮긴다(지금과 같은 값).
3. **결과 대본**: 서버 응답을 받은 뒤 집게-인형 연결(Constraint)을 붙인다. 잡힘 → 배출구 위에서 떼고 배출구 한가운데로 맞춰 떨어뜨림. 놓침(lift · chute · loose) → 서버 `slip`이 정한 순간(올라가는 45% · 배출구 쪽 60% · 쥐자마자)에 연결을 끊는다.
4. **마지막 순간 보정**: 놓친 인형이 배출구 칸막이를 넘으려 하면 칸막이 오른쪽으로 밀고 오른쪽 속도를 준다(시험 페이지 `chute`). 잡힌 인형이 튕겨 나가면 배출구로 끌어온다. 결과가 서버와 어긋나는 일은 없다.
5. 이번 V13.191 near-miss 연출(`claw-fx.js`)은 그대로 쓴다: 연결을 끊는 순간 = hit-stop, 떨어지기 시작 = 슬로모션.
